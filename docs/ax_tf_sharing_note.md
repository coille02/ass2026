# AX TF 공유 노트: AWS Summit Seoul 2026 Industry Day에서 본 전사 AX 도입 관점

## 공유 목적

이 문서는 AWS Summit Seoul 2026 Industry Day 참석 내용을 바탕으로, 사내 AX TF에서 논의할 만한 관점을 정리한 것이다. 대상 독자는 Summit 영상을 직접 보지 않았지만 Claude Code, Cursor, Amazon Q, Bedrock, 사내 LLM 도구 등 AI 개발 도구를 이미 사용해 본 개발자와 각 부서 AX 담당자다.

핵심 메시지는 단순하다.

> 개인이 AI 도구를 잘 쓰는 단계에서, 전사가 재사용 가능한 AI 업무 능력과 에이전트 운영 체계를 만드는 단계로 넘어가야 한다.

## 왜 이 이야기가 AX TF에 중요한가

현재 많은 개발자는 Claude Code 같은 도구로 코드 작성, 리팩터링, 테스트 작성, 문서화, 조사 업무를 빠르게 처리하고 있다. 하지만 이 방식은 대부분 개인 생산성에 머문다. 팀이나 전사 차원에서 보면 다음 문제가 남는다.

- 잘 만든 프롬프트와 워크플로가 개인 노트에 흩어진다.
- 부서별로 유사한 업무 자동화를 중복해서 만든다.
- 어떤 데이터와 도구를 AI가 써도 되는지 기준이 모호하다.
- AI가 만든 결과를 어떻게 평가하고 승인할지 체계가 약하다.
- 비개발자는 에이전트를 만들고 싶어도 도구 연결, 권한, 배포에서 막힌다.

Industry Day의 여러 사례는 이 문제를 공통적으로 보여준다. 성공 사례들은 AI 모델 자체보다, 업무와 데이터와 권한을 AI가 실행 가능한 구조로 바꾼 점이 핵심이었다.

## Summit 사례에서 보인 공통 패턴

### 1. AX는 챗봇 도입이 아니라 업무 능력의 구조화다

GS SHOP의 영상 추천 사례는 영상을 단순히 요약하지 않았다. 영상 속 장면, 분위기, 사용 맥락을 `소구 포인트`라는 추천 가능한 신호로 구조화했다. 즉, 원천 데이터 자체보다 "업무에 필요한 형태로 의미를 재구성하는 것"이 핵심이었다.

사내 AX에서도 마찬가지다. 문서 요약, 로그 분석, VOC 분류, 요구사항 정리, SQL 변환 같은 업무를 그냥 프롬프트로 처리하는 데서 끝내면 재사용성이 낮다. 이를 명확한 입력, 출력, 판단 기준, 사용 가능한 도구, 검증 방식이 있는 업무 스킬로 만들어야 한다.

### 2. 스킬허브는 프롬프트 저장소가 아니라 사내 업무 능력 카탈로그다

AX TF에서 가장 먼저 만들 만한 것은 `Skill Hub`다. 다만 단순 프롬프트 모음이면 부족하다. 스킬 하나는 다음 정보를 가져야 한다.

- 어떤 업무를 해결하는가
- 입력 데이터는 무엇인가
- 어떤 사내 시스템이나 문서에 접근하는가
- 출력 형식은 무엇인가
- 사람이 반드시 확인해야 하는 지점은 어디인가
- 품질 평가는 어떻게 하는가
- 누가 소유하고 관리하는가
- 어떤 부서에서 이미 검증했는가

예시 스킬:

- 장애 로그 1차 분석
- 회의록에서 액션아이템 추출
- VOC/CS 문의 유형 분류
- 신규 기능 PRD 초안 작성
- SQL/레거시 코드 현대화 후보 탐지
- 월간 지표 리포트 초안 작성
- 보안 리뷰 체크리스트 생성
- 고객 응대 스크립트 초안 작성
- 사내 규정 기반 질의응답

### 3. 비개발자용 Agent Builder가 필요하다

여러 사례에서 중요한 흐름은 에이전트가 개발자 전용 도구에 머물지 않는다는 점이다. 웅진씽크빅은 교육 현장 업무를, 롯데백화점은 고객 경험을, 아모레퍼시픽은 뷰티 상담을, 현대자동차는 시장 정보 분석을 AI 에이전트 구조로 풀었다.

우리 회사에서도 비개발자가 직접 업무 에이전트를 만들 수 있는 플랫폼이 필요하다. 다만 완전 자유형이어서는 안 된다. 안전한 구조는 다음과 같다.

- 승인된 스킬만 선택 가능
- 승인된 데이터 커넥터만 연결 가능
- 승인된 액션만 실행 가능
- 민감 데이터 접근은 권한 기반으로 제한
- 실행 로그와 비용 로그를 남김
- 배포 전 테스트와 승인 절차를 거침

즉, 비개발자가 만드는 것은 "아무거나 하는 AI"가 아니라, 검증된 업무 블록을 조합한 업무 에이전트여야 한다.

### 4. AI-ready data가 없으면 Agent Builder도 오래 못 간다

SK텔레콤의 데이터 플랫폼 사례는 AX TF에 특히 중요하다. 기존 데이터 플랫폼은 사람이 쿼리하고 분석하기 위한 구조였다. 하지만 AI 시대에는 에이전트가 데이터를 찾고, 의미를 이해하고, 권한 안에서 사용할 수 있어야 한다.

AX 관점에서 필요한 데이터 준비는 다음과 같다.

- 부서별 핵심 문서와 데이터 위치 파악
- 데이터 소유자와 접근 권한 정리
- 메타데이터와 용어 사전 구축
- 사내 시스템 API 목록화
- AI가 사용 가능한 문서와 사용 금지 문서 구분
- 데이터 품질과 최신성 관리

스킬허브와 Agent Builder는 결국 데이터와 도구 레이어 위에서 동작한다. 이 기반이 약하면 에이전트는 그럴듯한 답변은 하지만 실제 업무 수행은 못 한다.

### 5. Human-in-the-loop는 선택이 아니라 기본 설계다

삼성전자, 빗썸, 공공/규제 환경 세션에서 반복된 메시지는 거버넌스였다. 에이전트가 업무를 실행할수록 권한, 승인, 감사, 롤백, 평가가 중요해진다.

사내 AX 플랫폼에도 다음 원칙이 필요하다.

- 조회와 실행 권한을 분리한다.
- 민감 업무는 사람 승인 후 실행한다.
- 모든 에이전트 실행 로그를 남긴다.
- 결과 품질을 평가하는 기준을 둔다.
- 비용과 토큰 사용량을 모니터링한다.
- 잘못된 실행을 중단하거나 되돌릴 수 있어야 한다.

개발자 입장에서 Claude Code를 쓰는 것과 전사 Agent Platform을 운영하는 것은 다르다. 개인 도구는 빠른 실험이 중요하지만, 전사 플랫폼은 통제 가능한 반복 실행이 중요하다.

## AX TF에서 논의할 만한 전사 구조

```text
AX Portal
  ├─ Skill Hub
  │   ├─ 승인된 업무 스킬
  │   ├─ 부서별 템플릿
  │   ├─ 품질 점수 / 사용량 / 담당자
  │   └─ 입력 / 출력 / 데이터 / 검증 기준
  │
  ├─ Agent Builder
  │   ├─ 비개발자용 워크플로 빌더
  │   ├─ 승인된 데이터 커넥터
  │   ├─ 승인된 액션/API
  │   └─ 테스트 / 평가 / 배포 절차
  │
  ├─ Data & Tool Layer
  │   ├─ 사내 문서 / DB / 업무 시스템 연결
  │   ├─ 권한 / 감사 로그
  │   ├─ API Gateway 또는 MCP 형태의 도구 연결
  │   └─ 데이터 카탈로그 / 메타데이터 / 용어 사전
  │
  └─ AgentOps / Governance
      ├─ 승인 흐름
      ├─ 품질 평가
      ├─ 비용 모니터링
      ├─ 보안 정책
      └─ 실패 / 오작동 대응
```

## AX TF가 바로 해볼 수 있는 실행안

### 1단계: 부서별 후보 업무 수집

각 부서에서 다음 기준으로 후보 업무를 수집한다.

- 반복 빈도가 높다.
- 입력과 출력이 비교적 명확하다.
- 사람이 검토하면 품질을 판단할 수 있다.
- 민감도와 실행 리스크가 낮거나 통제 가능하다.
- 자동화 효과를 숫자로 측정할 수 있다.

수집 양식 예시:

| 항목 | 내용 |
|---|---|
| 업무명 | 예: 장애 로그 1차 분석 |
| 담당 부서 | 예: 플랫폼 운영팀 |
| 현재 처리 방식 | 사람이 로그와 알림을 확인해 원인 후보 정리 |
| 입력 데이터 | CloudWatch 로그, 알림 메시지, 배포 이력 |
| 출력 | 원인 후보, 영향 범위, 다음 조치 |
| 빈도 | 일 N회 |
| 예상 효과 | MTTR 단축, 야간 대응 부담 감소 |
| 리스크 | 잘못된 원인 판단, 민감 로그 노출 |
| 사람 승인 필요 여부 | 필요 |

### 2단계: 공통 스킬 10개 선정

부서별 후보를 모아 중복되는 업무를 찾는다. 전사 공통성이 높은 스킬부터 만든다.

추천 후보:

- 회의록 요약 및 액션아이템 추출
- 문서 기반 Q&A
- 장애/알림 1차 분석
- VOC/문의 분류
- 보고서 초안 작성
- 요구사항/PRD 초안 작성
- SQL/코드 변환 보조
- 테스트 케이스 생성
- 보안 체크리스트 생성
- 지표 이상 탐지 설명

### 3단계: 개발자용 레퍼런스 에이전트 먼저 만든다

이미 Claude Code를 쓰는 개발자들이 많다면, 개발자 업무부터 표준화하면 빠르게 성과를 낼 수 있다.

예시:

- PR 리뷰 보조 에이전트
- 장애 로그 분석 에이전트
- 레거시 코드 설명 에이전트
- 테스트 생성 에이전트
- API 명세 초안 생성 에이전트
- 배포 영향도 분석 에이전트

이 과정에서 스킬 포맷, 권한 모델, 로그 수집, 평가 기준을 먼저 검증한다. 이후 비개발자용 Agent Builder로 확장한다.

### 4단계: 비개발자 Agent Builder로 확장

개발자 레퍼런스가 안정화되면 현업이 직접 조합할 수 있는 화면을 만든다.

필수 기능:

- 스킬 선택
- 데이터 소스 선택
- 출력 형식 선택
- 실행 주기 설정
- 승인자 지정
- 테스트 실행
- 결과 평가
- 배포 요청

비개발자가 만드는 에이전트의 예:

- 주간 영업 리포트 초안 생성
- 고객 문의 유형별 요약
- 캠페인 성과 분석 초안
- 경쟁사 뉴스 모니터링
- 계약/정책 문서 질의응답
- 신규 입사자 온보딩 Q&A

## 발표에서 강조하면 좋을 메시지

### 개발자 대상 메시지

Claude Code를 잘 쓰는 것은 AX의 시작점이다. 하지만 전사 AX는 개인의 프롬프트 역량을 조직의 재사용 가능한 업무 능력으로 바꾸는 일이다.

### 부서 AX 담당자 대상 메시지

AI 도입 과제는 거창한 신사업보다 반복적이고 측정 가능한 업무에서 시작하는 것이 좋다. 업무를 스킬로 정의할 수 있다면 에이전트화할 수 있다.

### 리더 대상 메시지

AX 플랫폼의 핵심 투자는 모델 비용이 아니라 데이터, 권한, 승인, 평가, 운영 체계다. 에이전트가 많아질수록 AgentOps와 거버넌스가 경쟁력이 된다.

## 결론

AWS Summit Seoul 2026 Industry Day의 사례들은 서로 다른 산업 이야기처럼 보이지만, AX 관점에서는 하나의 메시지로 모인다.

> AX의 다음 단계는 개인이 AI를 잘 쓰는 것이 아니라, 회사의 반복 업무를 스킬화하고, 승인된 스킬과 데이터를 조합해 누구나 안전하게 에이전트를 만들 수 있는 플랫폼을 갖추는 것이다.

따라서 우리 AX TF가 논의할 핵심 과제는 다음 세 가지다.

1. 어떤 업무를 전사 공통 스킬로 만들 것인가
2. 비개발자가 안전하게 에이전트를 만들 수 있는 최소 플랫폼은 무엇인가
3. 데이터, 권한, 평가, 승인, 비용 관리를 어떤 기준으로 운영할 것인가
