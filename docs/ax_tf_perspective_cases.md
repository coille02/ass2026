# AX TF 공유용: AWS Summit 사례를 전사 AX 관점으로 읽기

## 공유 메시지

AWS Summit Seoul 2026 Industry Day에서 본 사례들은 특정 AWS 서비스 소개라기보다, 각 회사가 AI를 조직의 일하는 방식 안에 어떻게 넣고 있는지를 보여줬다.  
특히 우리처럼 Claude Code류 도구를 이미 쓰는 개발자들이 많은 조직에서는, 다음 질문이 중요하다.

> 개인이 AI 도구를 잘 쓰는 수준을 넘어, 전사에서 재사용 가능한 업무 스킬과 안전한 에이전트 운영 체계를 어떻게 만들 것인가?

아래는 Summit 사례를 AX TF 관점으로 다시 묶은 것이다.

## 1. 스킬허브: 프롬프트 모음이 아니라 업무 능력 카탈로그

**관련 사례**

- GS SHOP: 영상 속 장면과 분위기를 `소구 포인트`로 구조화해 추천 신호로 활용
- 웅진씽크빅: 교육 현장 업무를 AI-DLC 기반 교육자용 에이전트로 전환
- 현대자동차: 시장 정보 수집과 분석을 AI for MI 업무 흐름으로 구조화
- 포스코: 예지정비 모델 개발 업무를 현장 엔지니어가 활용 가능한 프로세스로 단축

**느낀 점**

가장 인상적이었던 부분은 AI를 "잘 물어보는 도구"로 쓰는 것이 아니라, 업무에 필요한 판단 단위를 새로 정의했다는 점이다. GS SHOP은 영상을 그대로 요약하지 않고 추천에 필요한 `소구 포인트`만 추출했다. 이건 우리 회사에도 중요하다. 사내 업무를 자동화하려면 프롬프트를 잘 만드는 것보다, 그 업무에서 반복적으로 필요한 판단 단위가 무엇인지 먼저 정의해야 한다.

스킬허브도 단순히 좋은 프롬프트를 모아두는 저장소가 되면 금방 낡는다. 각 스킬은 입력, 출력, 참조 데이터, 담당자, 검증 기준, 승인 필요 여부까지 포함하는 업무 능력 단위여야 한다.

**우리 TF에 던질 질문**

- 우리 회사에서 반복적으로 쓰이는 업무 판단 단위는 무엇인가?
- 부서마다 따로 만들고 있는 유사 프롬프트나 자동화는 없는가?
- 스킬 하나를 등록할 때 최소한 어떤 메타데이터가 필요할까?
- 스킬의 품질과 최신성은 누가 관리할 것인가?

**바로 해볼 일**

- 부서별로 반복 업무 10개씩 수집한다.
- 그중 전사 공통성이 높은 업무를 묶어 공통 스킬 후보 20개를 만든다.
- 스킬 등록 양식에 `입력`, `출력`, `참조 데이터`, `검증 기준`, `Owner`, `Human review 필요 여부`를 포함한다.

## 2. Agent Builder: 비개발자도 안전하게 에이전트를 만들게 하기

**관련 사례**

- 웅진씽크빅: 교육자와 학습 컨설턴트 업무를 AI 에이전트로 지원
- 롯데백화점: 고객 경험을 잇는 쇼핑 AI 에이전트 구축
- 아모레퍼시픽: 피부/두피/컬러 진단과 상담 경험을 AI 뷰티테크 플랫폼으로 확장
- AB180: RAG 챗봇을 SaaS 업무를 수행하는 Airbridge Pilot 에이전트로 발전
- Sendbird: 기억하는 AI 컨시어지를 통한 고객 경험 자동화

**느낀 점**

비개발자용 Agent Builder는 AX 확산에 매우 중요해 보였다. 부서별 업무는 현업이 가장 잘 알고 있는데, 매번 개발팀이 자동화를 만들어주는 방식으로는 속도가 나지 않는다. 다만 완전 자유형 빌더는 위험하다. 아무 데이터나 연결하고 아무 액션이나 실행할 수 있으면 Shadow AI와 다를 바 없다.

좋은 방향은 "승인된 블록을 조합하는 방식"이다. 비개발자는 검증된 스킬, 승인된 데이터 커넥터, 허용된 액션을 조합하고, 위험한 실행은 승인 흐름을 거치게 해야 한다. 즉 Agent Builder는 자유로운 실험 도구이면서 동시에 가드레일이 있는 운영 도구여야 한다.

**우리 TF에 던질 질문**

- 현업이 직접 만들 수 있는 에이전트의 범위는 어디까지인가?
- 조회형 에이전트와 실행형 에이전트를 어떻게 구분할 것인가?
- 에이전트가 사용할 수 있는 데이터 커넥터와 액션은 누가 승인할 것인가?
- 배포 전 테스트와 승인 절차는 얼마나 가볍게 가져갈 수 있을까?

**바로 해볼 일**

- 처음에는 실행형보다 조회/요약/분류형 에이전트부터 허용한다.
- Agent Builder의 최소 기능을 `스킬 선택`, `데이터 선택`, `출력 형식 선택`, `테스트 실행`, `승인 요청`으로 정의한다.
- 현업용 파일럿으로 주간 리포트, VOC 분류, 회의록 액션아이템 추출 같은 저위험 업무를 선정한다.

## 3. AI-ready Data: 에이전트가 이해하고 사용할 수 있는 데이터 기반

**관련 사례**

- SK텔레콤: AI에게 필요한 데이터 플랫폼, SageMaker Unified Studio와 Lake Formation 기반 데이터 거버넌스
- 현대지에프홀딩스: 전사 MLOps 플랫폼 기반 데이터 혁명
- 미래에셋증권: GraphRAG 기반 상품 지식 DB
- 아모레퍼시픽: 상담 노하우와 진단 데이터를 AI-ready data로 전환

**느낀 점**

Summit 사례를 보면 AX의 병목은 모델 성능보다 데이터 준비에 있는 경우가 많았다. 사람이 보기 좋은 데이터와 에이전트가 사용할 수 있는 데이터는 다르다. 에이전트는 데이터 위치, 의미, 권한, 최신성, 출처를 알아야 한다. 이게 없으면 답변은 그럴듯하지만 실제 업무 수행은 막힌다.

우리 회사도 Agent Builder를 만들려면 먼저 데이터와 도구 카탈로그가 필요하다. 어떤 문서를 AI가 봐도 되는지, 어떤 DB는 어떤 권한으로 조회 가능한지, 어떤 API는 실행 가능한지 정리되어야 한다.

**우리 TF에 던질 질문**

- AI가 사용할 수 있는 사내 문서와 사용할 수 없는 문서를 구분하고 있는가?
- 부서별 핵심 데이터의 Owner와 접근 권한은 명확한가?
- 용어 사전, 메타데이터, 데이터 계보가 에이전트가 이해할 수 있는 형태인가?
- 사내 시스템 API는 에이전트 도구로 제공할 준비가 되어 있는가?

**바로 해볼 일**

- 부서별 핵심 문서/DB/API 목록을 수집한다.
- AI 사용 가능, 제한적 사용, 사용 금지로 데이터 등급을 나눈다.
- 사내 용어 사전과 메타데이터 카탈로그를 에이전트가 검색 가능한 형태로 만든다.

## 4. 개발자 AX와 AI-DLC: Claude Code 사용을 조직 역량으로 승격하기

**관련 사례**

- 삼성전자: AI-DLC와 AIOps를 결합한 에이전틱 AI 전략
- 웅진씽크빅: Kiro와 AI-DLC로 교육자용 AI 에이전트 구축
- LG전자: 에이전틱 AI 기반 멀티에이전트 플랫폼
- 여기어때: Kiro CLI로 Oracle to Aurora MySQL 데이터베이스 현대화
- 놀유니버스: AWS Transform for .NET과 Kiro로 .NET 현대화
- 빗썸: Claude Code on Amazon Bedrock을 금융권 통제 환경에서 운영

**느낀 점**

개발자들은 이미 Claude Code 같은 도구로 개인 생산성 향상을 경험하고 있다. 하지만 Summit 사례에서 보인 차이는 개인 도구 사용을 개발 생애주기 전체로 확장했다는 점이다. 요구사항 정의, 설계, 코드 작성, 테스트, 배포, 운영까지 AI가 들어가고, 사람은 검토와 판단을 맡는 구조다.

우리도 개발자들이 각자 잘 쓰는 프롬프트와 워크플로를 모아 팀 단위 표준으로 만들 필요가 있다. 예를 들어 PR 리뷰, 테스트 생성, 로그 분석, 배포 영향도 분석 같은 개발자 스킬은 전사 공통성이 높다. 개발자용 레퍼런스 에이전트를 먼저 만들면 이후 비개발자 Agent Builder로 확장하기도 쉽다.

**우리 TF에 던질 질문**

- 개발자들이 현재 Claude Code를 어떤 업무에 가장 많이 쓰고 있는가?
- 개인별 프롬프트/워크플로를 팀 표준 스킬로 만들 수 있는가?
- 코드 생성 결과를 검증하는 기준과 테스트 자동화는 충분한가?
- 사내 코드와 민감 정보가 외부 모델로 나가지 않도록 통제하고 있는가?

**바로 해볼 일**

- 개발자 대상 AI 사용 사례를 수집한다.
- `PR 리뷰 보조`, `테스트 케이스 생성`, `장애 로그 분석`, `레거시 코드 설명`, `API 명세 초안`을 개발자 공통 스킬 후보로 만든다.
- Claude Code류 도구 사용 가이드와 보안 기준을 함께 정리한다.

## 5. AIOps와 AgentOps: 운영 자동화는 에이전트의 가장 현실적인 적용처

**관련 사례**

- 삼성전자: 대규모 계정 시스템 운영에 AIOps, SecOps, FinOps 에이전트 적용
- 요기요: SRE 운영의 콘솔 탈출기
- 야놀자: Multi-Agent 기반 AIOps와 Bedrock AgentCore
- 넥슨: 18만 개 모델을 운영하는 에이전틱 Ops
- 두산 디지털이노베이션: 자율 예지정비와 Agentic AI

**느낀 점**

운영 업무는 에이전트 적용에 매우 적합해 보였다. 이유는 입력 데이터가 많고, 반복 패턴이 있으며, 결과를 비교적 명확히 평가할 수 있기 때문이다. 장애 알림, 로그, 배포 이력, 메트릭, 런북은 에이전트가 읽고 정리하기 좋은 데이터다.

하지만 운영 자동화는 위험도도 높다. 처음부터 자동 조치까지 열기보다, 1차 분석과 원인 후보 제시, 영향 범위 요약, 관련 런북 추천부터 시작하는 것이 안전하다. 이후 신뢰도가 쌓이면 승인 기반 실행으로 확장할 수 있다.

**우리 TF에 던질 질문**

- 우리 운영 조직에서 반복되는 장애 대응 패턴은 무엇인가?
- 로그, 메트릭, 알림, 배포 이력을 한 화면에서 에이전트가 읽을 수 있는가?
- 에이전트가 추천한 원인과 조치의 품질을 어떻게 평가할 것인가?
- 자동 실행을 허용한다면 어떤 액션부터 허용할 것인가?

**바로 해볼 일**

- 장애/알림 1차 분석 에이전트를 파일럿으로 만든다.
- 처음에는 자동 조치 없이 원인 후보, 영향 범위, 관련 런북, 다음 조치만 출력한다.
- MTTR, 야간 대응 부담, 재분석 시간 감소를 지표로 본다.

## 6. Governance: 에이전트가 많아질수록 통제가 경쟁력이다

**관련 사례**

- 빗썸: 금융권 환경에서 Claude Code on Amazon Bedrock을 통제형으로 운영
- 공공/규제 환경 세션: 통제 가능한 AI 에이전트 아키텍처
- Datadog: 책임감 없는 AI 에이전트의 소유권 문제
- 삼성전자: Human-in-the-loop와 내부 경유 구조

**느낀 점**

전사 AX에서 가장 과소평가되기 쉬운 영역이 거버넌스다. 개인이 Claude Code를 쓰는 것과 회사가 에이전트를 운영하는 것은 다르다. 회사 에이전트는 데이터 접근, 도구 실행, 비용 사용, 결과 책임이 모두 남는다.

따라서 처음부터 조회 권한과 실행 권한을 분리하고, 민감 업무는 승인 후 실행하게 해야 한다. 모든 실행 로그와 비용 로그를 남기고, 어떤 에이전트가 어떤 데이터와 도구를 썼는지 추적 가능해야 한다.

**우리 TF에 던질 질문**

- 에이전트 실행 결과의 책임자는 누구인가?
- 에이전트별 권한 모델은 사용자 권한을 따를 것인가, 서비스 계정을 따를 것인가?
- 모든 실행을 감사 로그로 남길 수 있는가?
- 비용 폭증이나 잘못된 실행을 중단하는 장치가 있는가?

**바로 해볼 일**

- AgentOps 최소 기준을 만든다.
- 기준에는 권한, 로그, 승인, 평가, 비용, 데이터 등급, 금지 액션을 포함한다.
- 파일럿 에이전트도 이 기준을 통과해야 배포되도록 한다.

## 7. 산업 현장 AX: 현장 문제는 작아 보여도 효과는 크다

**관련 사례**

- 포스코: 광양제철소 설비 예지정비
- GS칼텍스: 현장이 만드는 제조 AI 전환
- 현대자동차: AI 기반 마켓 인텔리전스
- Config, 위로보틱스, SK인텔릭스: 피지컬 AI와 로보틱스
- 하나투어/제주항공: 여행 산업 업무 혁신

**느낀 점**

AX는 꼭 거대한 전사 프로젝트에서만 시작할 필요가 없다. 오히려 현장 반복 업무에서 시작한 사례들이 설득력이 있었다. 현장은 문제와 성과가 명확하다. 예지정비, 시장 정보 분석, 현장 보고, 품질 점검, 고객 문의 분류처럼 반복되고 측정 가능한 업무가 많다.

AX TF가 부서별 과제를 발굴할 때도 "AI로 멋진 것"보다 "반복 빈도가 높고 효과 측정이 가능한 것"을 우선해야 한다.

**우리 TF에 던질 질문**

- 각 부서에서 매주 반복되는 수작업은 무엇인가?
- 데이터는 이미 있는데 사람이 해석하느라 시간이 걸리는 업무는 무엇인가?
- 자동화 결과를 숫자로 측정할 수 있는가?
- 현업 담당자가 직접 검증할 수 있는가?

**바로 해볼 일**

- 부서별 AX 후보를 `빈도`, `효과`, `리스크`, `데이터 준비도` 기준으로 점수화한다.
- 높은 점수의 후보를 스킬허브 파일럿으로 등록한다.
- 4주 단위로 사용량과 절감 시간을 측정한다.

## 8. 고객 경험 AX: AI는 내부 생산성뿐 아니라 경험 설계도 바꾼다

**관련 사례**

- GS SHOP: 영상 기반 상품 추천
- 롯데백화점: AI 쇼핑 에이전트
- 아모레퍼시픽: AI 뷰티 상담과 진단 플랫폼
- Amazon Connect 계열 고객 AI Agent
- Sendbird: 기억하는 AI 컨시어지

**느낀 점**

고객 경험 영역에서 인상적인 점은 AI가 단순 응답 자동화가 아니라 고객 맥락을 기억하고 다음 행동을 제안하는 방향으로 가고 있다는 것이다. GS SHOP은 고객이 클릭한 상품 자체보다 왜 반응했는지를 보려 했고, 아모레퍼시픽은 상담사의 경험을 표준화된 AI 진단 경험으로 확장했다.

우리 회사도 고객 접점이 있다면 단순 챗봇보다 고객 여정의 어느 지점에서 맥락을 이해하고 다음 행동을 돕게 할지 봐야 한다.

**우리 TF에 던질 질문**

- 고객이 반복해서 묻거나 헷갈리는 지점은 어디인가?
- 고객 행동 데이터에서 의도 신호를 추출할 수 있는가?
- 상담/영업/운영 담당자의 암묵지를 AI 스킬로 구조화할 수 있는가?
- 고객-facing AI에 필요한 승인과 안전장치는 무엇인가?

**바로 해볼 일**

- 고객 문의와 상담 로그를 기반으로 주요 의도 20개를 분류한다.
- 상담사나 영업 담당자의 우수 답변 패턴을 스킬화한다.
- 고객-facing 적용 전 내부 상담 보조부터 파일럿한다.

## AX TF 공유용 결론

Summit 사례를 종합하면, 우리 AX TF가 가져가야 할 방향은 다음과 같다.

1. 개인 AI 도구 사용을 전사 스킬허브로 모은다.
2. 개발자용 레퍼런스 에이전트부터 만들어 표준을 검증한다.
3. 이후 비개발자도 승인된 스킬과 데이터를 조합할 수 있는 Agent Builder로 확장한다.
4. AI-ready data와 도구/API 카탈로그를 병행해서 만든다.
5. AgentOps와 Governance를 처음부터 포함한다.

마지막으로 공유 자리에서 이렇게 정리하면 좋다.

> Claude Code를 잘 쓰는 개발자가 많아진 것은 좋은 출발점이다.  
> 이제 AX TF의 역할은 그 개인 생산성을 전사적으로 재사용 가능한 업무 스킬, 안전한 에이전트 플랫폼, 그리고 통제 가능한 운영 체계로 바꾸는 것이다.
