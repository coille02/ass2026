# [빗썸] 빗썸은 생성형 AI를 어떻게 안전하게 운영하는가: Claude Code on Amazon Bedrock

## 발표 주제

이 세션은 Claude Code를 금융권 환경에서 안전하게 운영하기 위해 빗썸이 어떤 아키텍처와 통제 체계를 만들었는지 공유한 발표다. Claude Code를 개인 구독형 도구처럼 쓰는 것이 아니라, Amazon Bedrock을 LLM API 제공자로 두고 인증, 네트워크, 감사, 비용, 프롬프트 정책을 함께 설계한 과정이 중심이다.

발표는 먼저 Claude Code on Amazon Bedrock의 개념을 설명한 뒤, 빗썸이 AI 코딩 도구를 도입하게 된 배경과 요구사항을 소개했다. 이어서 초기 PoC 구조와 한계, LLM Gateway를 추가한 운영 아키텍처, 보안 검토와 거버넌스, 향후 확장 방향을 순서대로 다뤘다.

## 주요 내용

- Claude Code는 개발자 로컬 환경에서 실행되는 터미널 기반 AI 코딩 도구이며, 기본 Anthropic 계정 대신 Amazon Bedrock을 LLM API 제공자로 설정할 수 있다.
- Bedrock을 사용하면 Claude 모델을 AWS 인프라 위에서 호출할 수 있고, 프라이빗 네트워크, AWS 기반 감사, 사용량 기반 비용 추적 같은 기업 운영 요구사항을 붙이기 쉽다.
- 빗썸은 24시간 365일 운영되는 디지털 자산 거래소로, 빠른 개발 속도와 금융권 수준의 통제를 동시에 만족해야 했다.
- 공식 도구를 제공하기 전에는 개인 계정 기반의 외부 AI 도구 사용이 확산되고 있었고, 소스코드나 내부 설계 문서가 외부 서비스에 입력될 수 있는 위험이 있었다.
- 빗썸은 Claude Code 도입을 위해 SSO 기반 인증, 프라이빗 네트워크, 감사 로그, 예산과 비용 관리, 프롬프트 필터링을 핵심 요구사항으로 정의했다.
- Claude Max, Claude Enterprise, Amazon Bedrock 기반 구성을 비교한 결과, 네트워크 경로 통제와 멀티 모델 선택지, 기존 AWS 보안 서비스 재사용 측면에서 Bedrock 기반 구성이 가장 적합하다고 판단했다.
- 초기 PoC는 개발자 PC에서 Claude Code를 실행하고 AWS SSO와 IAM Role을 통해 Bedrock을 직접 호출하는 구조였다. 이 구조는 프라이빗 네트워크와 Shadow IT 대응에는 효과가 있었지만, 팀별 비용 추적과 상세 사용 이력 관리는 부족했다.
- 이후 Claude Code와 Bedrock 사이에 LLM Gateway를 두어 사내 인증 연동, 사용 정책 적용, 비용 추적, 감사 로그, 모델 라우팅을 중앙에서 처리하도록 확장했다.
- 오픈소스 기반 LLM Gateway는 공급망 공격 위험을 고려해 미러링, SAST/취약점 분석, AI 코드 리뷰, 보안 담당자 승인 후 배포되는 검증 파이프라인을 거치도록 구성했다.
- 향후에는 Claude 스킬과 프롬프트를 조직 카탈로그로 관리하고, 코드 리뷰, 테스트, 배포, 문서화 같은 개발 라이프사이클 전반에 AI를 더 안전하게 연결하는 방향을 제시했다.

## 세부 내용

### Claude Code on Amazon Bedrock의 의미

발표 초반에는 Claude Code와 Amazon Bedrock의 관계를 정리했다. Claude Code는 개발자 로컬 환경에서 실행되며 코드 작성뿐 아니라 코드베이스 탐색, 터미널 작업, 문서화 등 다양한 개발 작업을 지원한다. 이때 Claude Code의 백엔드 LLM API 제공자를 Amazon Bedrock으로 설정하면, Anthropic 계정으로 직접 로그인해 사용하는 방식과 다른 운영 모델을 만들 수 있다.

Bedrock을 사용하면 AWS 인프라 안에서 Claude 모델을 호출할 수 있고, 단일 리전, 교차 리전, 글로벌 엔드포인트 같은 선택지도 활용할 수 있다. 발표에서는 이 구성이 기업과 금융권 환경에서 중요한 이유로 세 가지를 들었다. 첫째, 인터넷을 직접 경유하지 않는 프라이빗 네트워크 구성이 가능하다. 둘째, CloudTrail과 CloudWatch 같은 AWS 서비스를 활용해 감사와 관측 체계를 만들 수 있다. 셋째, API 사용량 기반으로 팀별·개인별 비용 추적과 통제를 붙일 수 있다.

### 도입 배경과 요구사항

빗썸은 AI 코딩 도구 도입 배경으로 세 가지를 설명했다. 현업과 개발 조직에서 AI 도구 수요가 빠르게 증가했고, 개인 계정 기반 외부 AI 도구 사용이 확산되면서 전사 차원의 관리 필요성이 커졌으며, AI 기반 개발 생산성 향상이 조직 차원의 과제로 올라왔다는 점이다.

발표에서는 좋은 도구를 고르는 것만으로는 충분하지 않다고 강조했다. 빗썸은 Claude Code를 평가하면서 코드 이해도, 컨텍스트 유지력, 터미널 통합, 확장성 등을 봤고 높은 만족도를 확인했다. 하지만 금융권 환경에서는 도구의 생산성보다 안전한 운영 조건이 먼저 충족되어야 했다.

그 결과 핵심 요구사항은 다섯 가지로 정리됐다. 개별 API 키 대신 사내 계정 체계와 연결되는 SSO 기반 인증이 필요했고, LLM 호출은 인터넷을 직접 경유하지 않는 프라이빗 네트워크를 통해야 했다. 누가 어떤 모델을 사용했는지 추적할 수 있는 감사 로그, 팀과 개인 단위 비용 관리, 민감 정보나 정책 위반 입력을 탐지하고 차단하는 프롬프트 필터링도 필수 조건으로 정의됐다.

### 선택지 비교와 Bedrock 기반 구조

빗썸은 Claude Max, Claude Enterprise, Amazon Bedrock 기반 구성을 비교했다. Claude Max는 개인 사용에는 적합하지만 SSO 미지원, 개인 결제, 조직 관리와 감사 추적의 어려움 때문에 회사 차원의 도입에는 맞지 않았다. Claude Enterprise는 기업 관리 기능과 SSO를 제공하지만, 네트워크 통제와 데이터 처리 경로, 리전 선택, 벤더 종속성 측면에서 요구사항을 완전히 만족시키기 어렵다고 판단했다.

Bedrock 기반 구성은 프라이빗 네트워크와 서울 리전 기반 구성이 가능하고, 특정 벤더에 묶이지 않는 멀티 모델 선택지를 제공한다는 점이 장점으로 제시됐다. 또한 이미 운영 중인 IAM, SCP, CloudTrail, CloudWatch 같은 AWS 보안·운영 서비스를 재사용할 수 있다. 다만 Bedrock 단독으로는 사용자 인증, 예산 관리, 사용 정책 같은 중앙 관리 계층이 부족하므로 별도의 LLM Gateway를 붙이는 방향으로 설계가 확장됐다.

### 초기 PoC와 LLM Gateway

초기 PoC는 개발자 PC에서 Claude Code를 실행하고 AWS SSO 인증을 거쳐 IAM Role 기반으로 Bedrock을 직접 호출하는 구조였다. 네트워크는 Direct Connect와 PrivateLink 기반 전용 경로를 사용해 인터넷 구간을 제거했다. 이 구성만으로도 Shadow IT를 줄이고 프라이빗 네트워크를 확보하는 초기 목표는 달성할 수 있었다.

하지만 규모가 커지면 중앙 통제가 필요해진다. 팀별 비용 추적, 상세 사용 이력 관리, 모델 사용 패턴 분석, 일관된 운영 정책 적용이 필요했기 때문이다. 이를 위해 Claude Code와 Bedrock 사이에 LLM Gateway를 배치했다. LLM Gateway는 사내 인증 연동, 사용 정책 적용, 비용 추적, 감사 로그, 모델 라우팅을 담당하고, 사용 현황과 모델 사용 패턴을 중앙에서 볼 수 있게 했다.

발표에서는 LLM Gateway 자체도 보안 검토 대상이라고 설명했다. 오픈소스 기반 컴포넌트는 공급망 공격 위험이 있으므로, 새 버전이 나오면 사내 미러로 동기화하고 SAST와 취약점 분석, AI 코드 리뷰를 거친다. 이후 보안 담당자가 리포트를 확인하고 승인한 버전만 운영 환경에 배포되는 구조를 만들었다.

### 보안과 거버넌스

보안 파트에서는 금융권 생성형 AI 도입에서 필요한 통제 지점을 구체적으로 다뤘다. 인증은 SSO를 통해 사용자와 권한을 식별하고, 권한은 IAM Role과 SCP로 제한한다. 네트워크는 Direct Connect와 PrivateLink를 통해 통제 가능한 경로로 구성한다. 사용 이력과 감사 추적은 CloudTrail과 CloudWatch를 활용해 남기고, 비용은 사용자와 팀 단위로 확인할 수 있게 한다.

프롬프트와 응답에 대한 통제도 중요한 주제였다. 민감 정보나 정책 위반 가능성이 있는 입력을 탐지하고 차단해야 하며, 허용된 모델과 사용 정책을 기준으로 요청을 라우팅해야 한다. 발표에서는 보안이 단일 제품으로 해결되는 것이 아니라 인증, 네트워크, 로깅, 비용, 프롬프트 정책이 함께 설계되어야 한다는 점이 반복적으로 강조됐다.

### 확장 방향

발표 후반에는 Claude Code 사용 경험을 조직 자산으로 전환하는 방향이 소개됐다. 개발자들이 만든 Claude 스킬과 프롬프트를 카탈로그 형태로 관리하고, 코드 리뷰, 테스트, 배포, 문서화 같은 작업 유형별로 분류해 다른 팀에서도 재사용할 수 있게 하겠다는 계획이다.

또한 MR 코드 리뷰를 시작으로 개발, 배포, 운영 전 과정에 AI를 내재화해 더 안전한 코드가 서비스로 이어지도록 하는 방향도 언급됐다. 단순히 개발자에게 AI 도구를 열어주는 것을 넘어, 개발 라이프사이클 전체에서 보안과 생산성을 함께 높이는 구조로 확장하려는 접근이다.

## 정리

이 세션의 핵심은 Claude Code를 안전하게 쓰기 위한 조건을 아키텍처 요구사항으로 구체화했다는 점이다. 빗썸은 개인 구독형 AI 도구 사용에서 생길 수 있는 Shadow IT, 데이터 유출, 감사 추적 부재, 비용 통제 문제를 Bedrock, LLM Gateway, AWS 보안·운영 서비스 조합으로 풀었다.

금융권에서 생성형 AI를 도입할 때 중요한 것은 도구 자체의 성능만이 아니다. 누가 쓰는지, 어떤 경로로 호출되는지, 어떤 모델을 쓰는지, 비용과 로그가 어떻게 남는지, 민감 정보가 어떻게 차단되는지를 함께 설계해야 한다는 점이 발표의 핵심 메시지였다.
