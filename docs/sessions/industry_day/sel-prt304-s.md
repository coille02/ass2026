## 발표 주제

이 세션은 Agentic AI 시대에 기업이 로그, 메트릭, 트레이스 같은 machine data를 어떻게 관리해야 하는지 설명한 발표다. Splunk는 AI 에이전트가 장애 원인과 영향도를 판단하려면 모델 성능뿐 아니라 운영 데이터를 수집하고 검색하고 연결할 수 있는 데이터 기반이 먼저 필요하다고 강조했다.

발표는 기업 환경의 machine data가 보안, 개발, 운영 도메인별로 흩어져 있는 문제를 짚고, schema-on-read, SPL, Cisco Data Fabric, machine data lake를 통해 위치와 형식이 다른 데이터를 분석 가능한 구조로 만드는 전략을 제시했다.

## 주요 내용

- AI 에이전트가 운영 판단을 하려면 로그, 메트릭, 트레이스 등 machine data를 볼 수 있어야 한다.
- Kubernetes 노드, 애플리케이션 로그, VPC Flow Logs처럼 현대 인프라는 막대한 데이터를 생성하지만 이를 AI가 활용 가능한 상태로 정리하는 조직은 제한적이다.
- 보안, 애플리케이션, 개발, 운영 데이터가 분리되어 있으면 장애가 보안 이슈인지 시스템 이슈인지 빠르게 판단하기 어렵다.
- Splunk의 schema-on-read는 먼저 데이터를 저장하고 필요할 때 스키마를 적용해 다양한 형식의 machine data에서 인사이트를 얻는 접근이다.
- SPL은 여러 소스의 데이터를 검색, 필터링, 상관분석하는 언어로 소개됐다.
- Cisco Data Fabric과 machine data lake는 데이터가 S3, Snowflake, Databricks 등에 있더라도 분석과 검색이 가능하도록 연결하는 구조로 설명됐다.

## 세부 내용

### Agentic AI와 machine data

발표자는 ChatGPT 이후 생성형 AI 활용이 빠르게 확산됐지만, 기업 환경에서는 AI가 실제 운영 업무에 필요한 machine data에 접근하지 못해 활용도가 제한된다고 설명했다. 에이전트가 장애를 분석하거나 보안 이벤트를 판단하려면 애플리케이션 로그, 인프라 메트릭, 네트워크 흐름, 트레이스가 함께 필요하다.

이 데이터가 흩어져 있으면 AI는 충분한 맥락 없이 답변하게 된다. Splunk는 에이전트 시대의 기반이 GPU나 모델만이 아니라, AI가 읽고 추론할 수 있는 machine data 관리 체계라고 강조했다.

### 데이터 사일로와 관찰 가능성

현대 시스템은 Kubernetes, 마이크로서비스, 클라우드 네트워크, 보안 도구 등 여러 계층에서 데이터를 만든다. 그러나 각 데이터가 다른 저장소와 형식에 있으면 문제가 발생했을 때 원인과 영향도를 연결하기 어렵다.

Splunk는 보안과 운영, 개발 데이터가 연결되어야 장애 대응과 보안 분석이 빨라진다고 설명했다. AI 에이전트도 이 연결된 데이터를 기반으로 해야 의미 있는 판단을 할 수 있다. 결국 관찰 가능성은 사람뿐 아니라 AI가 운영을 이해하기 위한 전제 조건이다.

### Splunk의 관리 전략

schema-on-read는 데이터를 수집할 때 모든 구조를 미리 확정하지 않고, 분석 시점에 필요한 스키마를 적용하는 방식이다. 이 접근은 다양한 machine data가 빠르게 늘어나는 환경에서 유연성을 제공한다.

Cisco Data Fabric과 machine data lake는 데이터 위치를 하나로 강제하지 않고도 검색과 분석을 가능하게 하는 구조로 소개됐다. 데이터가 Amazon S3나 Snowflake, Databricks에 있더라도 필요한 분석을 수행할 수 있게 연결하는 것이 목표다.

## 정리

이 세션의 핵심은 Agentic AI를 운영에 쓰려면 AI가 볼 수 있는 machine data 기반이 먼저 필요하다는 점이다. 로그, 메트릭, 트레이스가 분리되어 있으면 AI도 장애와 보안 이벤트를 제대로 판단하기 어렵다.

Splunk가 제시한 전략은 데이터를 한곳으로 무리하게 모으는 것보다, 위치와 형식이 다른 데이터를 검색하고 연결할 수 있는 구조를 만드는 것이다. 에이전트 시대의 운영 경쟁력은 AI가 판단할 수 있는 데이터 환경에서 출발한다.
