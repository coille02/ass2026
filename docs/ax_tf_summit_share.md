# AX TF 공유용: AWS Summit Seoul 2026에서 본 전사 AX 도입 관점

## 한 줄 메시지

Claude Code 같은 개인 생산성 도구를 잘 쓰는 것은 AX의 출발점이다. 전사 AX의 다음 단계는 개인의 사용 경험을 부서별 업무 스킬, 안전한 에이전트 플랫폼, AI-ready data, 운영과 거버넌스 체계로 바꾸는 것이다.

## 공유 대상

- AWS Summit에 참가하지 않은 AX TF 구성원
- 이미 Claude Code, Cursor, Copilot류 도구를 업무에 쓰는 개발자
- 각 부서의 AX 과제를 발굴하고 수집해야 하는 담당자
- 비개발자까지 포함한 전사 AI 활용 체계를 고민하는 사람

## Summit에서 본 큰 흐름

Industry Day는 여러 회사가 AI를 실제 업무에 어떻게 넣고 있는지 보여줬다. GS SHOP의 영상 기반 상품 추천, 제조와 유통 현장의 데이터 분석, 고객 경험 자동화, 사내 업무 효율화 사례가 중심이었다.

AI Day는 그 사례를 가능하게 하는 기반을 더 깊게 다뤘다. Bedrock, SageMaker, AgentCore, Strands Agents, Kiro, AI-ready data, 보안, AIOps, 추론 인프라 같은 주제가 반복적으로 등장했다.

두 날을 합쳐 보면 메시지는 꽤 명확하다. “좋은 모델을 도입하자”가 아니라 “업무가 AI를 쓸 수 있는 형태로 정리되어 있는가”가 관건이다.

## AX TF 관점별 정리

### 1. Skill Hub: 프롬프트 모음이 아니라 업무 능력 카탈로그

가장 인상적인 지점은 AI 활용이 단순 질의응답이 아니라 반복 가능한 업무 단위로 쪼개지고 있다는 점이다. GS SHOP 사례처럼 영상 전체를 요약하는 것이 아니라, 추천에 필요한 쇼핑 사인, 스타일, 분위기 같은 판단 단위를 뽑아내야 실제 업무 가치가 생긴다.

우리 회사에서 Skill Hub를 만든다면 “좋은 프롬프트 저장소”로 끝나면 안 된다. 각 스킬에는 입력, 출력, 참조 데이터, 검증 기준, 담당자, 사용 권한, Human review 필요 여부가 같이 있어야 한다.

AX TF가 바로 해볼 일:

- 부서별 반복 업무를 10개씩 수집한다.
- 그중 공통성이 높은 업무를 스킬 후보로 묶는다.
- 스킬 등록 양식을 만든다: 입력, 출력, 데이터, 검증 기준, Owner, 권한, 리뷰 필요 여부.

### 2. Agent Builder: 비개발자도 만들되, 안전한 블록만 조합하게 하기

비개발자가 직접 에이전트를 만드는 플랫폼은 AX 확산에 중요하다. 다만 아무 데이터나 연결하고 아무 액션이나 실행할 수 있으면 Shadow AI가 더 커진다.

좋은 방향은 검증된 스킬, 승인된 데이터 커넥터, 허용된 액션을 조합하는 방식이다. 비개발자는 업무 흐름을 설계하고, 플랫폼은 권한과 실행 경계를 보장해야 한다.

AX TF가 바로 해볼 일:

- 조회형 에이전트와 실행형 에이전트를 분리한다.
- 첫 단계는 요약, 분류, 초안 작성, 리포트 생성처럼 위험이 낮은 업무로 제한한다.
- 실행형 액션은 승인 절차와 로그를 기본값으로 둔다.

### 3. AI-ready Data: 모델보다 먼저 데이터 사용 가능성을 점검하기

Summit 사례들을 보면 병목은 모델 성능보다 데이터 준비인 경우가 많다. 에이전트가 업무를 하려면 데이터의 위치, 의미, 권한, 최신성, 출처를 알아야 한다.

전사 Agent Builder나 Skill Hub를 만들려면 먼저 AI가 접근해도 되는 데이터와 접근하면 안 되는 데이터를 구분해야 한다. 데이터 카탈로그, 권한 정책, 문서 최신성 관리가 AX 플랫폼의 기반이 된다.

AX TF가 바로 해볼 일:

- 부서별 핵심 문서와 시스템을 AI 사용 가능 여부 기준으로 분류한다.
- 공개 가능, 사내 제한, 부서 제한, 민감 정보 포함 같은 등급을 정한다.
- RAG나 에이전트 연결 전에 출처 표시와 권한 필터링을 필수 요구사항으로 둔다.

### 4. AI-DLC: 개발 프로세스 자체를 AI 기준으로 다시 보기

AI Day에서 반복된 개발자 관점의 메시지는 AI가 코딩 보조를 넘어 개발 라이프사이클 전체에 들어온다는 점이다. 요구사항 정리, 설계, 코드 생성, 테스트, 배포, 운영 피드백까지 이어지는 AI-DLC 관점이 중요하다.

Claude Code를 잘 쓰는 개발자가 많은 조직이라면 다음 질문이 필요하다. 개인이 잘 쓰는 방법을 어떻게 팀 표준으로 만들 것인가. 어떤 산출물은 AI로 만들고, 어떤 의사결정은 사람이 책임질 것인가.

AX TF가 바로 해볼 일:

- 개발 조직에서 실제로 쓰는 AI 활용 패턴을 수집한다.
- 요구사항, 테스트, 코드 리뷰, 장애 분석 등 단계별 베스트 프랙티스를 정리한다.
- 프로젝트 템플릿에 AI 사용 규칙, 검증 체크리스트, 보안 금지사항을 포함한다.

### 5. AgentOps와 Governance: 만들기보다 운영이 더 어렵다

에이전트는 배포 후에도 계속 평가하고 관찰해야 한다. 답변 품질, 비용, 지연 시간, 권한 위반, 환각, 실패율을 봐야 한다. 특히 업무 실행형 에이전트는 로그와 승인 체계가 없으면 조직 리스크가 된다.

AX TF는 실험을 막는 조직이 아니라, 실험을 안전하게 반복할 수 있게 하는 조직이어야 한다. 이를 위해 최소한의 공통 운영 기준이 필요하다.

AX TF가 바로 해볼 일:

- 에이전트 등록부를 만든다: 목적, Owner, 사용 데이터, 권한, 비용, 로그 위치.
- 운영 지표를 정의한다: 성공률, 재작업률, 비용, 응답 시간, 사용자 만족도, Human review 비율.
- 보안팀과 함께 금지 데이터, 금지 액션, 승인 필요 액션을 정한다.

## 내부 공유 시 강조하면 좋은 포인트

1. AX는 도구 도입이 아니라 업무 재설계다.
2. 개인 생산성 향상은 이미 시작됐다. 이제 전사 재사용성과 안전성이 과제다.
3. Skill Hub는 프롬프트 모음이 아니라 업무 능력 단위의 제품 카탈로그여야 한다.
4. Agent Builder는 자유도가 아니라 통제된 조합 가능성이 핵심이다.
5. AI-ready data와 거버넌스가 없으면 에이전트는 PoC에서 멈춘다.

## 제안하는 다음 액션

AX TF에서 바로 시작할 수 있는 4주짜리 실험은 다음과 같다.

1. 1주차: 부서별 반복 업무와 AI 사용 사례를 수집한다.
2. 2주차: 공통 스킬 후보 20개를 정의하고 등록 양식을 만든다.
3. 3주차: 조회형 에이전트 2개와 문서 생성형 스킬 2개를 파일럿으로 만든다.
4. 4주차: 사용 로그, 품질, 보안 이슈를 보고 AgentOps 기준 초안을 만든다.

이 실험의 목표는 거대한 플랫폼을 바로 만드는 것이 아니다. 전사 AX 플랫폼이 어떤 스킬 단위, 데이터 기준, 운영 기준을 가져야 하는지 작게 검증하는 것이다.
