# AWS Summit Seoul 2026 AX 관점 통합 정리

AWS Summit Seoul 2026을 Industry Day와 AI Day로 나눠 보면 흐름이 꽤 선명하다. Industry Day는 여러 회사가 실제 업무와 고객 경험에 AI를 어떻게 넣었는지 보여줬고, AI Day는 그 사례를 가능하게 하는 데이터, 에이전트, 보안, 운영, 인프라를 다뤘다.

전체를 묶어서 보면 결론은 하나다. AX는 AI 도구를 더 많이 쓰게 하는 일이 아니다. 반복되는 업무를 재사용 가능한 스킬로 만들고, 비개발자도 안전하게 조합할 수 있게 하며, 데이터와 권한을 정리하고, 운영과 감사가 가능한 구조로 만드는 일이다.

Claude Code, Cursor, Amazon Q, Bedrock, 사내 LLM 도구를 잘 쓰는 것은 출발점이다. 전사 AX는 그 다음 단계, 즉 개인의 생산성을 조직의 운영 체계로 바꾸는 일에 가깝다.

## 1. Skill Hub는 프롬프트 저장소가 아니다

GS SHOP은 영상에서 추천에 필요한 신호를 뽑았고, 바비톡은 리뷰 검수와 상담 같은 업무 단위를 에이전트로 확장했다. 빗썸은 Claude Code 사용 경험을 조직 스킬과 프롬프트 카탈로그로 축적하려 했다. 이 사례들이 공통으로 말하는 것은 스킬의 의미다.

스킬은 “좋은 프롬프트”가 아니다. 반복 가능한 업무 능력이다. 좋은 스킬은 다음 정보를 함께 가져야 한다.

- 어떤 입력을 받는가
- 어떤 출력을 만드는가
- 어떤 데이터와 도구를 참조하는가
- 누가 사용할 수 있는가
- 결과를 어떻게 검증하는가
- 누가 관리하고 개선하는가
- 사람 승인이 필요한가
- 로그와 비용은 어떻게 남는가

따라서 Skill Hub를 만든다면 프롬프트 공유 게시판이 아니라 업무 능력 카탈로그로 설계해야 한다. 처음에는 개발자용 코드 리뷰, 테스트 작성, 문서화 스킬과 현업용 정책 검색, 문의 분류, 보고서 초안, 회의 준비 스킬을 나눠 시작할 수 있다.

## 2. Agent Builder는 자유도가 아니라 안전한 조합이 중요하다

비개발자도 에이전트를 만들 수 있는 플랫폼은 필요하다. 하지만 아무 데이터나 연결하고 아무 액션이나 실행할 수 있는 구조는 위험하다. 특히 금융 서비스에서는 데이터 민감도와 실행 권한이 모두 다르기 때문에 자유도가 곧 리스크가 될 수 있다.

좋은 Agent Builder는 검증된 블록을 조합하게 해야 한다. 승인된 데이터 커넥터, 승인된 스킬, 허용된 도구 호출, 정해진 출력 형식, 사람 승인 단계를 조합하는 방식이다.

초기에는 조회형, 요약형, 분류형, 초안 작성형 에이전트부터 시작하는 것이 현실적이다. 실행형 에이전트는 로그, 승인, 롤백, 권한, 장애 대응 기준이 준비된 뒤에 열어야 한다. 이 순서를 지켜야 확산 속도와 안정성을 같이 가져갈 수 있다.

## 3. 개발자 AI 플랫폼은 우선순위가 높다

빗썸의 Claude Code on Amazon Bedrock 사례는 개발자 AI 도구를 어떻게 다뤄야 하는지 좋은 기준을 줬다. 개인 계정과 외부 도구 사용을 막는 것만으로는 충분하지 않다. 개발자가 쓰기 편하면서도 회사가 통제할 수 있는 경로를 제공해야 한다.

필요한 구조는 비교적 명확하다.

- SSO 기반 인증
- 프라이빗 네트워크 또는 통제 가능한 모델 호출 경로
- 팀/개인별 비용 가시화
- 감사 로그와 사용 이력
- 민감 정보와 코드 반출 정책
- 모델 라우팅과 사용 정책
- 팀별 스킬과 시스템 프롬프트 공유

이 구조가 잡히면 개발자 AI 도구는 개인 생산성 도구에서 개발 플랫폼으로 올라간다. 코드 생성만이 아니라 코드베이스 탐색, 테스트, 리뷰, 배포 전 점검, 운영 문서화까지 연결할 수 있다.

## 4. 데이터 카탈로그가 없으면 AX는 데모에서 멈춘다

AI Day에서 반복된 가장 중요한 메시지는 데이터였다. 에이전트는 데이터의 위치, 의미, 권한, 최신성, 출처를 알아야 한다. OpenSearch, Snowflake, SK AX, 삼성 TV 데이터 질의, 완성차 상품 전략 플랫폼 같은 세션들은 모두 같은 문제를 다른 방식으로 풀고 있었다.

전사 AX를 하려면 먼저 데이터와 도구의 지도를 만들어야 한다. 사내 문서, 정책, 개발 문서, 장애 이력, 고객센터 지식, 상품 설명, 리스크 기준, 운영 대시보드, 이슈 시스템, 배포 시스템은 모두 접근 권한과 사용 목적이 다르다.

중요한 구분은 세 단계다.

1. AI가 검색해도 되는 데이터
2. AI가 답변 생성에 써도 되는 데이터
3. AI가 실행 판단에 써도 되는 데이터

이 구분 없이 Agent Builder를 열면 품질 문제와 보안 문제가 동시에 생긴다. 데이터 카탈로그와 권한 필터링은 AX 플랫폼의 부가 기능이 아니라 선행 조건이다.

## 5. 업무형 AI 데스크톱은 사무직 AX의 현실적인 방향이다

20만 Amazonian의 AI 내재화와 Quick Desktop 세션은 전사 확산의 방향을 잘 보여줬다. AI를 별도 챗봇으로 두는 것이 아니라, knowledge worker가 이미 쓰는 문서, 메일, 메시지, 캘린더, 스프레드시트, 대시보드, 파일 작업 흐름 안으로 넣는 방식이었다.

이 관점은 중요하다. 많은 사무직 업무는 한 번의 질문으로 끝나지 않는다. 아침에는 밤사이 쌓인 메시지와 이슈를 파악하고, 낮에는 회의와 자료를 준비하고, 오후에는 의사결정 초안과 후속 메일을 만들고, 퇴근 후에는 정해둔 작업이 이어진다. 업무형 AI는 이 흐름 전체를 도와야 한다.

따라서 사내 AI 포털을 만든다면 단순 Q&A보다 다음 기능을 우선 생각할 수 있다.

- 오늘 해야 할 일과 읽어야 할 이슈 요약
- 회의 전 관련 문서, 대시보드, 이슈 모음
- 보고서와 발표자료 초안 생성
- 이메일과 메시지 답변 초안
- 반복 리포트의 예약 실행
- 작업 진행 상태와 리스크 피드
- 사용자가 승인한 도구와 데이터만 연결

이 방향은 사무직 AX와 개발자 AX를 연결한다. 둘 다 결국 기존 도구와 데이터를 안전하게 연결해 업무 흐름을 줄이는 문제다.

## 6. AIOps와 운영 문서화는 빠르게 시작할 만하다

삼성 어카운트 AIOps, 넥슨의 에이전틱 Ops, 야놀자의 AIOps, POSCO의 예지정비 사례를 보면 운영 영역은 AX 효과가 비교적 빠르게 보일 수 있다. 장애와 이상 징후가 발생하면 사람이 로그를 보고, 알림을 묶고, 영향 범위를 추정하고, 조치 내용을 정리하고, 회고 문서를 작성한다. 이 과정은 반복적이고 문서화 부담이 크다.

다만 운영 에이전트는 신중해야 한다. 처음부터 자동 조치를 목표로 두기보다 다음 순서가 맞다.

1. 로그와 알림 요약
2. 영향 범위와 관련 시스템 후보 정리
3. 원인 후보와 확인 쿼리 제안
4. 공지와 회고 문서 초안 작성
5. 사람이 승인하는 조치 추천
6. 제한된 범위의 자동 실행

이렇게 가면 운영 리스크를 줄이면서도 AX 효과를 체감할 수 있다.

## 7. 서버리스 워크플로는 내부 자동화의 좋은 기본형이다

완성차 지능형 상품 전략 플랫폼은 외부 PDF와 웹 데이터를 수집하고, Bedrock으로 정보를 추출하고, Step Functions로 병렬 처리하고, S3·Glue·Athena로 분석 자산을 만드는 구조였다. 이 사례는 내부 자동화에도 잘 맞는다.

많은 부서 업무는 “여러 곳에서 가져와서, 맞춰보고, 정리하고, 보고하는” 흐름이다. AI는 추출과 요약을 맡고, 서버리스 워크플로는 반복 실행, 실패 처리, 재시도, 로그, 알림을 맡으면 된다. 챗봇보다 이런 워크플로형 AX가 실제 시간을 더 줄일 수 있다.

AX 과제를 볼 때는 화면보다 흐름을 먼저 봐야 한다. 수집, 추출, 검증, 저장, 알림, 승인, 보고서 생성 중 어디가 병목인지 찾는 것이 좋다.

## 8. 우선순위 제안

지금 단계에서 AX TF가 가져갈 우선순위는 다음 순서가 적당해 보인다.

1. 부서별 반복 업무를 스킬 후보로 수집한다.
2. Skill Hub 등록 양식을 만든다.
3. 개발자 AI 도구의 안전한 사용 경로를 설계한다.
4. 데이터 카탈로그와 권한 체계를 정리한다.
5. 조회형/요약형/분류형/초안형 에이전트부터 만든다.
6. 운영 문서화와 AIOps 보조를 빠른 실험 대상으로 잡는다.
7. 업무형 AI 포털 또는 데스크톱의 최소 기능을 정의한다.
8. 비용, 로그, 보안, 품질 평가 기준을 플랫폼 기본값으로 둔다.

## 9. 실제로 들은 세션에서 남은 생각

GS SHOP 세션에서는 추천을 위한 신호 추출이 가장 기억에 남았다. 혜택이나 상품 추천도 결국 좋은 메타데이터와 검증 가능한 근거가 있어야 한다.

K-POP 글로벌 라이브 세션에서는 AI 기능보다 운영 안정성이 크게 보였다. 고객 접점의 AI 기능은 장애 전환, 비용, 품질 폴백과 함께 설계되어야 한다.

바비톡 세션에서는 작게 시작하는 방식이 좋았다. 큰 플랫폼보다 반복 업무 하나를 실제로 줄이는 작은 성공이 먼저 필요하다.

빗썸 세션은 금융권에서 개발자 AI 도구를 어떻게 안전하게 운영할지 가장 직접적인 참고 사례였다.

삼성 어카운트 AIOps 세션은 대규모 서비스 운영에서 AI가 분석과 조치 후보 추천에 강점을 가질 수 있음을 보여줬다.

완성차 지능형 상품 전략 플랫폼 세션은 외부 자료 수집과 정규화, 전략 데이터 자산화를 서버리스 워크플로로 풀 수 있다는 점이 좋았다.

20만 Amazonian과 Quick Desktop 세션은 AI 내재화가 개인 도구 사용을 넘어 회사가 승인한 업무 환경과 스킬 체계로 가야 한다는 점을 보여줬다. 특히 기존 업무 도구를 연결하고, 개인 업무 맥락을 유지하며, 아침 요약과 퇴근 후 작업까지 이어주는 방향은 사무직 AX의 좋은 출발점으로 보인다.

전체 결론은 이렇다. 전사 AX는 더 많은 AI 도구를 쓰자는 캠페인이 아니다. 업무를 스킬로 정리하고, 데이터와 권한을 연결하고, 개발자와 비개발자가 안전하게 에이전트를 사용할 수 있게 만드는 운영 체계다.
