# AI Day에서 본 AX 플랫폼 관점

AI Day는 Industry Day보다 한 단계 더 플랫폼과 운영에 가까웠다. Bedrock, AgentCore, Strands Agents, Kiro, SageMaker, OpenSearch, Amazon Quick, 보안, AIOps, 추론 인프라, AI-ready data가 반복해서 등장했다. 메시지는 “AI를 써보자”가 아니라 “AI가 계속 쓰일 수 있는 구조를 만들자”에 가까웠다.

Industry Day가 실제 업무 사례를 보여줬다면, AI Day는 그 사례를 운영 가능한 서비스로 만들기 위해 무엇이 필요한지 보여줬다. 데이터, 권한, 관측성, 비용, 보안, 개발 프로세스, 변화관리까지 들어가야 한다.

## 1. 에이전트는 데모보다 운영이 어렵다

[삼성전자 삼성 어카운트의 에이전틱 AIOps](sessions/ai_day/sel-aim305.md)는 이 메시지를 가장 잘 보여줬다. AI PoC가 프로덕션으로 가지 못하는 이유는 모델 성능만의 문제가 아니다. 운영 우수성, 데이터, 신뢰, 안정성이 함께 준비되어야 한다. 대규모 사용자 서비스에서 에이전트가 장애 탐지, 원인 후보 정리, 조치 제안에 들어가려면 관측성, 권한, 예외 처리, 실패 대응이 필요하다.

운영 에이전트는 처음부터 자동 조치까지 열면 위험하다. 먼저 사람이 하던 상황 정리, 로그 요약, 영향 범위 추정, 공지 초안, 회고 문서 초안, 조치 후보 추천부터 시작하는 편이 현실적이다. 실행은 사람이 승인하고, AI는 근거와 후보를 정리하는 역할을 맡는 구조가 안전하다.

이 관점은 AgentOps에도 그대로 적용된다. 에이전트가 무엇을 봤고, 어떤 도구를 호출했고, 어떤 비용이 발생했고, 어디서 실패했는지 추적되지 않으면 운영 시스템으로 볼 수 없다.

## 2. AI-ready data가 Agent Builder의 전제다

AI Day에서 가장 반복적으로 나온 주제는 데이터였다. AI-ready data, 에이전틱 AI를 위한 데이터 실무, OpenSearch, Snowflake, SK AX의 통합 AI 환경, 삼성 TV 앱 데이터 자연어 질의 같은 세션은 모두 같은 문제를 다뤘다. 에이전트가 일을 하려면 데이터가 어디에 있고, 어떤 의미이며, 누가 볼 수 있고, 얼마나 최신이며, 어떤 출처를 갖는지 알아야 한다.

전사 Agent Builder를 만들려면 먼저 데이터 카탈로그가 있어야 한다. 사내 문서, 개발 문서, 정책, 장애 이력, 고객센터 지식, 상품 설명, 리스크 기준, 운영 대시보드는 모두 민감도와 권한이 다르다. “AI가 검색할 수 있다”와 “AI가 답변에 써도 된다”와 “AI가 실행에 사용해도 된다”는 서로 다른 권한이다.

따라서 데이터 준비는 후순위 작업이 아니다. AX 플랫폼의 첫 번째 기반이다.

- 데이터 소유자와 관리 책임
- 문서와 데이터의 최신성 기준
- 부서별 용어와 표준 명칭
- 권한 기반 검색과 필터링
- 출처 표시와 근거 추적
- 민감 정보 마스킹과 접근 제한
- 결과 품질을 평가할 기준 데이터

이것이 없으면 Agent Builder는 데모는 가능하지만 실무 도구로 확산되기 어렵다.

## 3. 개발 방식 자체가 AI-DLC로 바뀐다

Kiro, LG전자의 AI 기반 개발 라이프사이클, GitLab Duo, Strands Agents, 보안 강화 전략 세션들은 개발 과정 전체가 AI 기준으로 재편되고 있음을 보여줬다. 요구사항 정리, 설계, 코드 생성, 테스트, 보안 점검, 배포, 운영 피드백이 한 흐름으로 연결된다.

개발자 개인이 Claude Code나 Cursor를 잘 쓰는 것만으로는 팀 생산성이 안정적으로 올라가지 않는다. 팀마다 다른 방식으로 프롬프트를 쓰고, 검증 없이 생성 코드를 붙이고, 보안 기준이 흩어지면 오히려 기술 부채가 늘 수 있다.

필요한 것은 팀 표준이다.

- 에이전트가 읽을 요구사항과 설계 문서 형식
- 저장소별 코딩 규칙과 테스트 명령
- AI가 참조해도 되는 문서와 금지 데이터
- 생성 코드 리뷰 기준
- 보안 검사와 시크릿 탐지
- 배포 전 검증 루틴
- 실패와 리뷰 피드백을 다음 실행에 반영하는 방식

AI-DLC는 개발자를 대체하는 흐름이 아니라 개발팀의 작업 방식을 더 명시적으로 만드는 흐름에 가깝다. 사람이 암묵적으로 알고 있던 규칙을 문서와 자동화로 꺼내야 에이전트도 안정적으로 일할 수 있다.

## 4. 업무형 AI는 기존 도구와 연결될 때 의미가 커진다

[20만 Amazonian의 AI 내재화와 Quick Desktop](sessions/ai_day/sel-biz204.md)은 전사 확산 관점에서 가장 인상적인 세션이었다. 핵심은 챗봇을 하나 더 제공하는 것이 아니었다. knowledge worker가 이미 쓰는 문서, 메일, 메시지, 캘린더, 스프레드시트, 대시보드, 파일 작업 흐름에 AI를 연결하는 것이었다.

Quick Desktop은 개인별 업무 맥락을 지식 그래프처럼 이해하고, 아침에는 밤사이 쌓인 메시지와 메일을 요약하며, 미팅 전에는 관련 문서와 파일을 모아 자료 초안과 이메일 초안을 만들고, 퇴근 후에는 사용자가 맡긴 작업을 이어서 수행하는 방향으로 소개됐다. 이건 “질문하면 답하는 도구”보다 “하루의 업무 흐름을 정리하고 이어주는 업무 환경”에 가깝다.

전사 AX도 비슷한 방향을 고민할 수 있다. 각자가 개별 도구를 쓰는 단계에서 멈추면 사용 경험은 늘지만 조직 자산은 남지 않는다. 승인된 데이터, 승인된 도구, 공통 스킬, 로그, 비용 관리, 권한 체계가 함께 있어야 한다. 업무형 AI 데스크톱은 사내 포털, 문서, 일정, 메시지, 이슈, 결재, 대시보드를 연결하는 방향에서 출발할 수 있다.

## 5. 서버리스와 이벤트 기반 구조는 내부 업무 자동화에 잘 맞는다

[완성차 지능형 상품 전략 플랫폼](sessions/ai_day/sel-prt302-s.md)은 외부 PDF와 웹 데이터를 수집하고, Bedrock으로 정보를 추출하고, Step Functions로 병렬 처리하고, S3·Glue·Athena로 분석 가능한 자산을 만드는 사례였다. 이 사례의 핵심은 AI 모델보다 업무 흐름 전체를 서버리스 워크플로로 만든 점이다.

사내 업무에도 이런 패턴이 많다. 여러 시스템에서 데이터를 모으고, 명칭을 맞추고, 누락을 확인하고, 사람이 볼 수 있는 형태로 정리하는 일이다. 이때 AI는 추출과 정규화, 요약을 맡고, 서버리스 워크플로는 반복 실행과 실패 처리, 재시도, 로그를 맡는다.

AX 과제를 볼 때 “챗봇으로 답변”만 떠올리면 좁다. 수집, 추출, 검증, 저장, 알림, 승인, 보고서 생성까지 하나의 흐름으로 보는 편이 맞다.

## 6. 보안과 비용은 플랫폼의 기본 기능이다

AI Day의 보안, 추론 최적화, EKS, Trainium, AMD EPYC, OpenShift, Oracle, Snowflake 세션들은 AX가 커질수록 인프라와 비용 문제가 커진다는 점을 보여줬다. 초반에는 API 호출 비용만 보이지만, 실제로는 검색 인프라, 벡터 저장소, 로그, 평가 데이터, 배치 처리, 모델 라우팅, 권한 필터링, 관측성 비용이 함께 생긴다.

보안도 마찬가지다. AI가 데이터를 읽고 도구를 실행하는 순간, 기존 애플리케이션과 같은 수준의 인증, 인가, 감사, 변경 관리가 필요하다. 특히 개발 에이전트와 운영 에이전트는 코드, 이슈, 로그, 배포 도구와 연결될 수 있으므로 더 조심해야 한다.

AX 플랫폼의 기본 기능은 다음과 같아야 한다.

- 사용자와 에이전트의 인증/인가
- 도구 호출 로그와 감사 추적
- 민감 정보 탐지와 차단
- 모델별 비용과 사용량 가시화
- 프롬프트, 응답, 도구 호출의 관측성
- 실패 시 중단, 재시도, 사람 승인
- 모델과 인프라 선택 기준

## 7. AI Day에서 남는 실행 과제

AI Day를 기준으로 보면 AX 플랫폼 과제는 여섯 가지다.

1. Agent Builder 전에 데이터 카탈로그와 권한 체계를 만든다.
2. 개발자 AI 사용 경험을 AI-DLC 표준으로 승격한다.
3. 운영 에이전트는 자동 실행보다 분석, 요약, 추천, 문서화부터 시작한다.
4. 업무형 AI는 기존 도구와 연결되는 데스크톱/포털 경험으로 설계한다.
5. 서버리스 워크플로로 수집, 추출, 검증, 보고서 생성을 자동화한다.
6. 보안, 비용, 로그, 관측성을 플랫폼 기본 기능으로 둔다.

AI Day의 결론은 이렇다. 전사 AX는 좋은 모델을 고르는 문제가 아니라, 에이전트가 안전하게 데이터를 보고 도구를 쓰며 계속 개선될 수 있는 운영 체계를 만드는 문제다.
